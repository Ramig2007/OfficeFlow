Это **восстановление в независимый экземпляр базы на том же Docker-хосте**. Оно не доказывает хранение резервной копии вне VPS или восстановление после потери физической машины. Для этого нужны внешнее хранилище и отдельный хост.

Повторить на отдельном безопасном тестовом стенде, где развернут Docker Compose:

```bash
bash scripts/backup.sh
bash scripts/test-restore-independent.sh backups/officeflow-YYYYMMDDTHHMMSSZ.dump
```

Скрипт не меняет содержимое рабочей БД, но **сравнение числа строк с источником предполагает отсутствие новых записей между созданием дампа и проверкой**. Проводите сверку без параллельных изменений либо используйте согласованный snapshot.

## Как повторить проверку

Для Linux/VPS также добавлены `scripts/backup.sh` и `scripts/test-restore.sh`. Первый создаёт архив и SHA-256; второй выполняет полное восстановление во временную БД, сравнивает counts и проверяет constraint, не изменяя исходную БД:

```bash
bash scripts/backup.sh
bash scripts/test-restore.sh backups/officeflow-YYYYMMDDTHHMMSSZ.dump
```

Linux-скрипты добавлены в CI для проверки синтаксиса, но фактическое выполнение на VPS ещё не проводилось.

Запускать в **PowerShell из корня OfficeFlow**, где расположены `compose.yaml`, `.env` и `scripts/`.

## 1. Создать резервную копию

```powershell
.\scripts\backup.ps1
```

Скрипт уже входит в исходный проект. Он делает дамп PostgreSQL формата `pg_dump -Fc` и сохраняет его локально в `backups/officeflow-YYYYMMDD-HHmmss.dump`. Убедитесь, что файл появился и его размер больше нуля:

```powershell
Get-ChildItem .\backups\*.dump | Sort-Object LastWriteTime -Descending | Select-Object -First 3 Name, Length, LastWriteTime
```

## 2. Восстановить **только в отдельную временную БД** и сверить данные

```powershell
.\scripts\test-restore.ps1
```

Или передать явный путь:

```powershell
.\scripts\test-restore.ps1 -BackupFile .\backups\officeflow-YYYYMMDD-HHmmss.dump
```

Скрипт:
1. Находит последний `.dump` (или использует указанный), проверяет его размер.
2. Создаёт случайно названную временную базу `officeflow_restore_check_...` внутри уже существующего контейнера PostgreSQL.
3. Восстанавливает дамп командой `pg_restore --exit-on-error` исключительно в эту временную базу.
4. Сравнивает количество пользователей, комнат, бронирований, событий аудита и миграций с действующей базой (исходная база только читается).
5. Проверяет наличие критического ограничения `booking_room_no_overlap` (GiST exclusion).
6. Удаляет временную БД и временный файл дампа даже при большинстве ошибок.

**Успех:** строка `RESTORE_TEST_OK` и строка об удалении временной базы. Если количество записей отличается, во время резервного копирования или сверки данные могли измениться — повторите проверку без активных пользователей.

**Не запускайте** `scripts/restore.ps1`: он заменяет данные *действующей* базы, для этого этапа не нужен.

## Ограничения проверки

- Временная БД создаётся **в том же контейнере PostgreSQL**, но не затрагивает рабочую базу; требуется немного свободного места на диске.
- Сверка чисел не является проверкой идентичности каждой записи и не доказывает восстановление всего приложения после отказа узла.
- Для реальной эксплуатации храните копию вне компьютера/тома, шифруйте её, проверяйте ротацию и доступы.
- Сам скрипт требует фактической проверки на локальном стенде пользователя; не объявляйте restore успешным до получения `RESTORE_TEST_OK`.

## Удалённая копия и Lifecycle retention — подтверждение 22.11.2026

- Архив: officeflow-20261121T212120Z.dump.
- Источник: Neon PostgreSQL.

- Архив и файл SHA-256 загружены в приватный bucket officeflow-backups-2026, затем скачаны обратно; sha256sum -c вывел officeflow-20261121T212120Z.dump: OK.
- Workflow прочитал текущие Lifecycle rules и versioning, сохранил 1 стороннее правило, установил собственное правило officeflow-backups-retention-30-days для префикса officeflow/daily/, затем запросил конфигурацию обратно.
- Проверка завершилась сообщением: Yandex Object Storage lifecycle verified: OfficeFlow daily backups expire after 30 days.
- Политика: текущие объекты — 30 дней; незавершённые multipart uploads — 7 дней; для включённого/приостановленного versioning добавляется истечение нетекущих версий через 30 дней.

Это подтверждает сохранённую конфигурацию bucket через S3 API, а не фактическое удаление уже истёкших объектов: удаление выполняет Yandex Lifecycle по расписанию после достижения срока хранения.
