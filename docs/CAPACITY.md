# Состав оборудования, ПО и предварительная оценка ресурсов

## Исходные условия

Преподаватель задаёт **1000 одновременных пользователей**, **100 RPS**, доступность ≥99,9%, p95 ≤200 мс, долю ошибок ≤0,1%. Это **целевые параметры**, не измеренные характеристики OfficeFlow.

Консервативные расчётные предположения (подлежат уточнению бенчмарком):

- 1000 открытых браузерных сессий, но 100 HTTP-запросов в секунду; 1000 пользователей не равно 1000 исполняемых запросов одновременно.
- Нагрузка: 80% GET (календарь, комнаты, история), 20% POST/PATCH (встречи, согласование).
- 95% GET укладываются примерно в 50–150 мс в нормальном состоянии БД — **гипотеза**, а не доказательство.
- Среднее время ответа для модели 100 мс: по закону Литтла `L ≈ λ × W = 100 req/s × 0,1 s = 10` одновременно обрабатываемых запросов. При 200 мс — `20`; пиковый запас x2–3 → **40–60** серверных слотов.
- Плотность данных: 100 комнат, 1000 пользователей, 100000 бронирований в год, 20–40 аудиторских действий на бронирование в расширенной модели. В текущем коде журнал фиксирует основные операции, а не абсолютно каждый HTTP GET.
- Небольшое количество вложений (нет бинарных файлов); наиболее значимы таблицы Booking/AuditEvent, WAL, индексы и резервные копии.

## Компоненты

| Компонент | Назначение | Обоснование |
|---|---|---|
| Django + Gunicorn | REST, шаблоны, сервисная логика | единые правила для HTML/API, зрелая экосистема |
| PostgreSQL 16 | транзакции, брони, аудит | ACID, исключающие GiST constraints, индексы |
| Redis 7 | сессии/кэш | быстрый доступ, снижение числа повторных чтений |
| Nginx | reverse proxy, статика | небольшие накладные расходы, static caching |
| Prometheus | метрики | pull model и PromQL для SLA |
| Grafana | панели | визуализация p95, RPS, errors, up |
| Alertmanager | алерты | маршрутизация сигналов, требует реального receiver |
| k6 | воспроизводимая нагрузка | фиксированная скорость запросов и пороги |
| GitHub Actions | CI/CD | тесты и Docker-сборка при push |

## Предварительный производственный профиль

**Предложение для пилотирования, не подтверждённый размер кластера:**

| Узел | CPU | RAM | Диск | Допущение |
|---|---:|---:|---:|---|
| Django app ×3 | 3 × 2 vCPU | 3 × 2 GB | 3 × 10 GB | по 1 worker × 8 threads, итого 24 потока |
| PostgreSQL primary | 4 vCPU | 8 GB | 100 GB SSD | данные + индексы + WAL; backup отдельно |
| Redis | 1 vCPU | 1 GB | 10 GB | сессии, AOF |
| Nginx/LB | 1 vCPU | 512 MB | 5 GB | входящий прокси с TLS |
| Prometheus + Grafana | 2 vCPU | 4 GB | 50 GB | метрики и хранение |
| **Итого (округлённо)** | **14 vCPU** | **19,5 GB** | **195 GB** | не включает отдельный standby и внешний backup |

Это разделяемая по узлам оценка без гарантии RPS. Dev Compose содержит **1 приложение и 1 базу** — он служит для учебной демонстрации, не реализует эту трёхрепличную топологию. Для развертывания трёх реплик нужен конфиг внешнего LB или оркестратора и контроль миграций.

### Оценка базы

Допустим средний логический размер Booking с индексами ~1–2 KB, а AuditEvent ~0,4–1 KB (грубые верхнеуровневые оценки). Для 100k Booking/год ≈100–200 MB/год плюс значительный резерв под аудиты, WAL, bloating, VACUUM и миграции. Размер 100 GB SSD — запас на несколько лет и эксплуатационные операции, **не** точная оценка фактического использования. Реальные размеры проверяются `pg_total_relation_size(...)` в пилоте.

### Доступность

99,9% означает максимум около **43,2 минуты простоя за 30 дней** (30 × 24 × 60 × 0,001). Одна PostgreSQL DB — single point of failure; для реальных 99,9% нужны репликация/управляемая БД, external LB, отдельные backup, проверки recovery, TLS, мониторинг и измерение SLI. На учебном стенде SLA лишь задан.

### Верификация

1. Тест GET комнат и календаря: 100, затем 200 RPS; сохранить p50, p95, error rate, DB/Redis CPU и connections.
2. Нагрузить **авторизованные бизнес-запросы**, включая запись и конфликт на одну комнату.
3. Провести тест с искусственной задержкой SQL/ограничением ресурсов PostgreSQL; описать деградацию и 503/readiness.
4. Подобрать Gunicorn threads, размер пула, индексирование, кеширование по замерам, а не по желаемому числу.
5. После успешного теста обновить таблицу фактическими значениями. Объём базы, `pg_stat_statements`, `EXPLAIN ANALYZE`, slow queries — приложить к протоколу.
