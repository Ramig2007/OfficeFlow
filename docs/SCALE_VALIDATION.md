# OfficeFlow — план масштабных испытаний

## Назначение и безопасность

Масштабные испытания выполняются только в одноразовом Docker Compose окружении GitHub Actions. Оно создаёт собственные PostgreSQL/Redis volumes, использует DEBUG=1, синтетические аккаунты и уничтожает volumes после завершения. Не направляйте эти сценарии на production, публичный VPS или базу с реальными данными.

Workflow: .github/workflows/scale-validation.yml. Он запускается при push в ветку scale-validation/** или вручную после появления workflow в main. Результаты k6 и снимки docker stats сохраняются в GitHub Actions artifact officeflow-scale-validation на 90 дней.

## 1. 1000 независимых авторизованных сессий

Сценарий: scripts/loadtest-1000-users.js.

- Подготавливаются 1000 отдельных учётных записей loadtest01 … loadtest1000.
- Каждый виртуальный пользователь (VU) проходит отдельную HTML-авторизацию и получает собственную Django session cookie.
- Профиль нагрузки: ramp-up 100 → 250 → 500 → 750 → 1000 VU, удержание 1000 VU в течение 3 минут, затем плавное завершение.
- Каждый вошедший пользователь выполняет один авторизованный GET примерно раз в 10 секунд к одному из API маршрутов комнат, собственных бронирований или расписания.
- Условия успешного теста: пик не менее 1000 VU, 1000 успешных независимых входов, отсутствие неудачных логинов, HTTP error rate менее 1%, p95 менее 2 секунд, p99 менее 5 секунд и не менее 99% успешных проверок.

**Интерпретация:** 1000 VU — это 1000 одновременно поддерживаемых синтетических сессий в конкретном тестовом окружении, а не доказательство 1000 реальных людей, не гарантия производительности на любом VPS и не нагрузка 1000 запросов в секунду. При удержании один запрос на сессию примерно раз в 10 секунд соответствует около 100 запросам/с.

## 2. Нагрузка на создание, редактирование и отмену

Сценарий: scripts/loadtest-booking-create-edit-cancel.js.

Каждая итерация с собственной пользовательской сессией выполняет последовательный жизненный цикл:

1. POST /api/v1/bookings/ — создать уникальную бронь.
2. PATCH /api/v1/bookings/{id}/ — изменить название и проверить сохранённое значение.
3. POST /api/v1/bookings/{id}/cancel/ — отменить бронь и проверить статус.

Профиль: ramp-up от 5 до 10 и затем до 20 полных жизненных циклов в секунду; удержание максимального уровня 2 минуты. Верхняя ступень соответствует примерно 60 API write-запросам/с (20 create + 20 edit + 20 cancel). Для каждого VU зарезервирован отдельный временной слот. Между итерациями выдерживается пауза, чтобы не превышать лимит 120 API запросов в минуту на одного пользователя.

Условия успешного теста: HTTP error rate менее 1%, p95 менее 1,5 секунды, p99 менее 3 секунд, отсутствие пропущенных итераций, успешные проверки create/edit/cancel и отсутствие ошибок входа.

## 3. Ресурсные показатели

Во время обоих тестов workflow сохраняет периодические снимки docker stats для приложения, PostgreSQL, Redis, Nginx и контейнера k6. Сопоставляйте пики CPU/RAM с latency, ошибками и dropped iterations.

## 4. Ограничения результата

- GitHub-hosted runner имеет ограниченные CPU/RAM; это не эквивалент производственного сервера.
- Если тест не проходит, сохраняйте исходный результат, находите узкое место и повторяйте после конкретного исправления. Не ослабляйте пороги только ради зелёного статуса.
- Нагрузочные показатели действуют только для протестированных образов, конфигурации, размера runner и профиля запросов.
- 1000 сессий не означает 1000 активных одновременных HTTP операций.
- Даже успешный прогон не доказывает SLA 99,9%: для этого требуется длительное измерение на работающем публичном сервисе с внешней точки наблюдения.

## 5. Фактические результаты

Результаты не записываются заранее. После реального запуска workflow сюда следует добавить run URL, commit, пиковые VU, число успешных логинов, фактические операции/с, p95/p99, ошибки, dropped iterations и максимальные CPU/RAM. Сырые логи и JSON summary хранятся в artifact officeflow-scale-validation.
