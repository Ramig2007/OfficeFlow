# Руководство администратора и эксплуатации

## Назначение

OfficeFlow предназначен для управления переговорными и корпоративными встречами. Локальный демостенд разворачивается `docker compose up -d --build`. Полный сценарий PowerShell — в корневом `README.md`.

## Что делает администратор

1. Создаёт пользовательский аккаунт или назначает роль `admin` через меню «Пользователи». Первый суперпользователь создаётся командой `docker compose exec app python manage.py createsuperuser`.
2. Добавляет комнату с названием, этажом, расположением, вместимостью, оборудованием, статусом VIP.
3. Перед изменением VIP-флага проверяет будущие бронирования (программа запрещает такую смену, если активные встречи есть).
4. На странице «VIP-заявки» одобряет либо отклоняет ожидающую встречу с обязательным указанием причины отказа.
5. Фильтрует отчёты по датам/комнате и выгружает CSV. Исторические записи сохраняются после отмены.
6. Периодически проверяет readiness, графики, бэкапы, задержку и ошибки в приложении.

## Служебные команды (PowerShell из корня проекта)

```powershell
docker compose ps
docker compose logs --tail=100 app
docker compose logs --tail=100 db
docker compose exec app python manage.py check
docker compose exec app python manage.py showmigrations workspace
docker compose exec db pg_isready -U officeflow -d officeflow
```

Последняя строка использует типовые имена БД; при другой конфигурации замените `officeflow` значениями из `.env`.

## Healthcheck и monitoring

- `GET /health/live/`: процесс приложения отвечает (не проверяет зависимости).
- `GET /health/ready/`: проверяет `SELECT 1` в основной БД и set/get Redis cache. При сбое возвращает HTTP 503.
- Prometheus собирает `django_http_*` HTTP counters и histogram; PostgreSQL/Redis exporters собирают состояние зависимостей.
- Grafana: папка OfficeFlow, панель Reliability; проверять метрики RPS, p95, 5xx rate, availability.
- Prometheus alert rules созданы, но локальный Alertmanager использует **null-receiver**. Для получения инцидентов назначьте реальный webhook/email receiver и проверьте доставку. Без этого алерты не сообщают людям.

## Backup policy

1. Ежесуточный backup базы через `scripts/backup.ps1`; хранить вне рабочего диска в защищённом хранилище.
2. Рекомендуемая ротация для пилота: последние 7 ежедневных, 4 недельных копии. Данные и retention согласуйте с организацией.
3. Еженедельный тест восстановления в изолированной БД (не в основной).
4. Контролировать успешное завершение процесса, читаемость dump и время восстановления.
5. Задать реальные RPO и RTO после тестов; нельзя объявлять их достигнутыми заранее.

Команды:

```powershell
.\scripts\backup.ps1
# Прежде чем восстанавливать, СНИМИТЕ свежую резервную копию.
.\scripts\restore.ps1 -BackupFile .\backups\officeflow-YYYYMMDD-HHmmss.dump
```

Для Linux/VPS предусмотрены `scripts/backup.sh` и `scripts/test-restore.sh`:

```bash
bash scripts/backup.sh
bash scripts/test-restore.sh backups/officeflow-YYYYMMDDTHHMMSSZ.dump
```

Первый скрипт создаёт custom-format dump, проверяет его читаемость через `pg_restore --list` и сохраняет переносимый SHA-256. Второй восстанавливает архив во временную БД, сверяет counts основных таблиц и наличие GiST exclusion constraint, затем удаляет временную БД. Исходная БД используется только для чтения. Архив и checksum всё равно нужно копировать в отдельное зашифрованное хранилище за пределами VPS.

**Внимание:** `restore.ps1` передаёт дамп во временный файл контейнера PostgreSQL и вызывает `pg_restore --clean`. Эта операция меняет существующую БД. На продуктивной системе следует остановить запись/перевести приложение в maintenance, согласовать восстановление и верифицировать referential integrity после него. Скрипт рассчитан на простую локальную учебную среду; полноценный DR runbook должен учитывать последовательность отключения сервисов, повторный запуск, ротацию секретов и rollback.

## Безопасность

- `DEBUG=0` и длинный случайный `SECRET_KEY`; любой `.env` держать вне Git и с ограниченными правами.
- Для VPS используется `compose.production.yaml` с Caddy: он принимает 80/443, получает TLS-сертификат и проксирует запросы во внутренний Nginx. Nginx привязан к loopback на 8080 и передаёт `X-Forwarded-Proto` от Caddy в Django.
- Production overlay принудительно включает `DEBUG=0`, secure cookies, HTTPS redirect и HSTS. Заполнить `DOMAIN`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` и уникальные секреты в серверном `.env`; не коммитить его.
- Пользователь с `role=member` не получает доступ к админским данным; Django auth проверяет пароль с безопасными hashers.
- Никаких production credentials в `seed_demo`; демо отключено при `DEBUG=0`.
- Для пользователей с доступом к данным ограничивать retention audit logs; выполнять бэкапы с шифрованием. CSV может содержать названия корпоративных встреч и имена пользователей.
- Django REST Framework SessionAuthentication требует CSRF для unsafe-запросов сессии. Не отключайте CSRF middleware.
- `POST` для выхода, отмены и VIP-решения; URL GET только читают данные.
- Защита от IDOR в `BookingViewSet.get_queryset` и доменных сервисах.
- Django admin не редактирует и не удаляет Booking напрямую, чтобы не обходить бизнес-логику.
- Проект учебный: до промышленной эксплуатации нужны проверка зависимостей, внешние pen-test/DAST, политик паролей/SSO, секрет-хранилище и миграции без простоя.

## Порядок реагирования на инцидент

1. Получить сигнал (Grafana/Prometheus) и воспроизвести по readiness, logs.
2. Установить границу: Nginx, Django, PostgreSQL, Redis, внешняя сеть.
3. Для отказа БД: запретить новые записи, проверить free disk, WAL, active connections; не запускать `down -v`.
4. Для ошибок 409 конфликтов: это ожидаемая бизнес-ошибка, не 5xx. Исследовать несоразмерный рост отдельно.
5. Исправить, добавить регрессионный тест, перезапустить сервис с минимальным влиянием.
6. Сохранить хронологию инцидента: обнаружение, причина, ущерб, исправление, время восстановления и профилактика.

## Production deployment

Пошаговая инструкция DNS, firewall, HTTPS, создания администратора, проверки health endpoints и off-host backup находится в [`DEPLOYMENT.md`](DEPLOYMENT.md). Подготовленная конфигурация сама по себе не означает, что сайт уже размещён на публичном VPS.

## Ограничения демонстрационного стенда

Compose использует одну PostgreSQL, одну Redis, один Django контейнер, локальный Nginx с HTTP, Prometheus/Grafana без внешней аутентификации (порты ограничены loopback) и Alertmanager без реальной доставки. Это не HA-кластер. Не публиковать в Интернет без TLS, firewall, секретов, обновлений образов и hardening.
