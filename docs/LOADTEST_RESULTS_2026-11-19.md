# OfficeFlow — протокол нагрузочных тестов

## 1. Baseline liveness endpoint (19.11.2026)

Источник: фактический вывод Grafana k6. Среда: Docker Compose на компьютере разработчика, endpoint `/health/live/` через Nginx (`http://proxy`). Каждый прогон — 30 секунд.

| Прогон | План | Фактическая интенсивность | HTTP-запросов | HTTP 200 | Ошибки | p95 | Статус |
|---|---:|---:|---:|---:|---:|---:|---|
| Baseline A | 100 RPS | 99,99064 RPS | 3000 | 3000 | 0% | 1,40 мс | Пройден |
| Baseline B | 200 RPS | 199,945545 RPS | 6001 | 6001 | 0% | 1,49 мс | Пройден |

Первый ошибочный прогон 100 RPS (3001 запрос, 0 HTTP 200, p95 1040 мс) был конфигурационным: внутреннее имя `proxy` отсутствовало в `ALLOWED_HOSTS`. После исправления локального `.env` повторные прогоны прошли.

## 2. Авторизованное чтение HTML-страниц (19.11.2026)

Скрипт: `scripts/loadtest-auth-read.js`. Перед нагрузкой выполняется реальный вход через HTML-форму, затем одна авторизованная сессия выполняет GET-запросы к `/rooms/`, `/schedule/` и `/my-bookings/`. Сценарий использует constant-arrival-rate, 40 предварительно выделенных VU и максимум 200 VU.

| Прогон | План | Фактическая интенсивность | Итераций | HTTP-запросов | HTTP-ошибки | Среднее | p95 | Максимум |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Authenticated read A | 150 RPS | 149,316 RPS | 4500 | 4502 | 0 | 7,19 мс | 13,07 мс | 138,73 мс |
| Authenticated read B | 200 RPS | 199,215 RPS | 6001 | 6003 | 0 | 7,09 мс | 13,19 мс | 122,14 мс |

В прогоне 200 RPS все 6001 проверки завершились успешно; в выводе k6 указано 0 interrupted iterations. Порог скрипта: p95 <200 мс, HTTP failure rate <0,1%, checks >99,9%.

## 3. Что эти результаты доказывают

- На локальном Docker Compose стенде приложение обслуживало авторизованные GET-запросы к трём HTML-разделам с фактической скоростью около 199,2 HTTP req/s в течение 30 секунд.
- В этом прогоне p95 составил 13,19 мс, HTTP-ошибок не было.
- Отдельный baseline `/health/live/` прошёл на 100 и 200 RPS.

## 4. Что эти результаты НЕ доказывают

- Не тестировались POST/PATCH операции создания, редактирования, отмены или VIP-согласования под нагрузкой.
- Не моделировались 1000 независимых пользователей/сессий: authenticated read использовал одну авторизованную тестовую сессию.
- Не измерялась длительная доступность и SLA 99,9%.
- Не выполнялся fault injection PostgreSQL и не проверялось поведение при отказе БД.
- p95 baseline liveness нельзя выдавать за p95 бизнес-операций.

Для дальнейшего закрытия требований нужен отдельный изолированный write workload с несколькими тестовыми пользователями и отдельной тестовой БД. Не запускать его на базе с реальными данными.
