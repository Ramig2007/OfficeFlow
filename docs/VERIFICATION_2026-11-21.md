## 3. Изолированная нагрузка на запись

Сценарий: `scripts/loadtest-booking-write.js`, Grafana k6, HTTP API создания и отмены бронирований, 30 секунд, constant-arrival-rate **8 итераций/с**.

- Подготовлено 16 отдельных тестовых учётных записей; в измеренном прогоне было до **11 одновременно активных VU**, а не 16 одновременно работающих пользователей.
- **240 итераций**, каждая содержит успешное создание и отмену брони; всего **480 успешных операций записи**. Включая операции входа, **512 HTTP-запросов**.
- **720/720 проверок** успешны, **0 HTTP-ошибок**, **0 dropped iterations**.
- p95 HTTP latency — **16,92 мс**, среднее — **13,29 мс**, максимум — 205,72 мс.
- Зафиксировано около **7,72 завершённой итерации/с** за полный период k6, включающий завершение итераций.
- Итоговый критерий k6 (порог p95 <1000 мс, 0 dropped iterations, менее 1% HTTP failures, checks >99%) — пройден.

Проверка не подтверждает 100/200 RPS **записи** и 1000 независимых пользователей; предыдущий тест около 199,2 HTTP RPS относился к **чтению**.

## 4. Деградация инфраструктуры

В отдельном CI Compose-стенде поочерёдно останавливались и запускались сервисы:

- PostgreSQL: readiness HTTP **503** при отключении → HTTP **200** после восстановления.
- Redis: readiness HTTP **503** при отключении → HTTP **200** после восстановления.

Это подтверждает обнаружение отказа зависимостей и возврат readiness; не подтверждает HA, репликацию или нулевое время простоя.

## 5. Alertmanager и мониторинг

- Prometheus/Grafana Dashboard и правила alerting подготовлены ранее.
- В CI `amtool check-config` проверил обе конфигурации: безопасный `null-receiver` и необязательный HTTPS webhook receiver.
- Чтобы отправлять уведомления **реальным людям**, оператор должен задать `ALERTMANAGER_WEBHOOK_URL` (и при необходимости `ALERTMANAGER_WEBHOOK_BEARER_TOKEN`) только в локальном/серверном `.env`, запустить observability profile и проверить фактическую доставку. Пока endpoint не указан, уведомления не отправляются.
- Не записывать токены или персональные данные в Git.

## 6. Не закрыто только автоматическими CI-проверками

1. Публичный VPS, домен, TLS и внешние ручные проверки — требуются реальные сервер и доступы.
2. Off-host шифрованные резервные копии и восстановление на другой машине — требуется внешнее хранилище/сервер.
3. Реальная доставка алертов — нужен реальный HTTPS endpoint.
4. Репликация PostgreSQL, полноценное HA, работа 1000 одновременных пользователей и SLA 99,9% — не доказаны.
5. Независимое экспертное согласование и формальная приёмка — требуют участия преподавателя/рецензента.

**Вывод:** после PR #16 проект технически значительно лучше проверен и готов к локальной учебной демонстрации, но не следует называть его промышленно развёрнутым или имеющим доказанный SLA.
